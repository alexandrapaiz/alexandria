The kill-loop guard, probed live on 2026-10-24 during the rebase of #421.

Read-only. This probe reads /proc and kills nothing. It asks each live
next-server on the machine which directory it was started in, and reports what
main's kill loop would do to it against what this branch's does.

Five live next-server processes, and not one of them is ours. This harness had
not started a server yet when the probe ran.

The last row is the whole argument. /tmp/epito-ursa-frontend-WUyUPZ/ursa-minor
is another company's frontend seat, mid-run, on this machine, at the moment of
the probe. On main, the first act of `serve.sh` is to send that process a
signal, and the script says nothing about it afterwards because everything it
verifies from that line on is about our own port.

The four unreadable rows are other users' processes, which is why the readlink
fails, and sparing them is correct for the same reason it is correct to spare
the fifth.

The guard already on main is dated 2026-10-17 and it does not cover this. It
sits on the post-start stray check, which decides whether the script exits 1.
It kills nothing. The two guards read the same property of the same set and do
different things with the answer, which is why both comments stay in the file
and why the mechanism is now explained once, at the first of the two in reading
order, with the second pointing back at it.

The kill loop named all five and killed none, which is the guard working on a
live machine and not in a probe. The four unreadable processes were still alive
afterwards. The ursa one exited inside the window on its own and ursa started
another, 3852435, which also survived. The only processes this run killed were
3854613 and 3854639, both of them its own, checked by cwd before the signal.

Then the part that was not the guard, and it is a second finding.

serve.sh exited 1 and printed no reason at all. The last line it wrote is the
banner of the check it died inside. The cause is in the script rather than in
the server:

  served=$(curl -s "$BASE_FE/" | grep -o '/_next/static/css/[^"]*' | head -1)

`set -euo pipefail` is on at the top of the file. When the page references no
stylesheet, grep exits 1, pipefail hands that to the assignment, and set -e
aborts the script on the assignment itself. The `if [ -z "$served" ]` guard
underneath it, with its FAIL message, is one line too late and had therefore
never printed since the day it was written. The script's own comment above the
stray check says a guard that quietly does nothing is worse than no guard. This
one could not even announce itself.

Repaired by ending the pipeline with `|| true`, so the guard that was always
there can now run, and by giving it the status code and the known cause. Tested
against the live 500 from the run above:

  == proving the server is THIS build ==
  FAIL: the served page references no stylesheet at all.
        http://127.0.0.1:4903/ answered 500, so this is an error
        document rather than our markup. Read /tmp/next-serve.log.
        The known cause in this container is a missing Clerk
        publishable key: clerkMiddleware throws before any page
        renders, and the harness's __clerk_db_jwt cookie cannot help,
        because the middleware never reaches the handshake it cures.

The 500 itself is the environment and not the branch. `site/` has no env file
here and no Clerk publishable key is exported, so `clerkMiddleware` throws
inside the middleware bundle before any page renders. The harness's cookie cure
is for the dev-browser handshake, which is a later step than the one that
throws, so it cannot reach this. That is why this run verified the script and
did not re-shoot the sweep: the frames in this folder are from the run that had
a working server, the site diff under review has not changed since they were
taken, and photographing nine 500 pages tonight would have been evidence of
nothing.
