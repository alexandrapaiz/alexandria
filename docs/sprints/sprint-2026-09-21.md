   the queue** (see item 1 below), assigned to the engineer, due before
   Stripe goes live 2026-09-26. Security's floor statement named it the
   one genuine pre-launch security blocker: `/register` never persists a
   client's submitted `redirect_uris` and `/authorize` accepts whatever
   `redirect_uri` the request carries with no check against that
   registration, so a crafted link on the real domain plus the real
   passphrase hands an attacker a working token pair, including

   `register()` (line 501) echoes `redirect_uris` back in its response

   code against whatever `redirect_uri` the form posts, with no lookup
   against any stored registration. PKCE does not close this gap, since
   the attacker who crafts the link also holds the matching
   `code_verifier`.

## Backlog

1. **Fix the MCP OAuth redirect-URI validation gap** (engineer) —
   blocking, due before Stripe goes live 2026-09-26. `/register`
   (`mcp/server.py:501`) must persist each client's submitted
   `redirect_uris` (a signed token or a small store, engineer's choice)
   and `/authorize` and `/token` must reject any request whose
   `redirect_uri` does not match what was registered for that
   `client_id`. PKCE is not a substitute for this check; leave PKCE as
   is and add the registration check alongside it. Done means: a
   mismatched `redirect_uri` is rejected before a code or token is ever
   minted, an automated test not requiring a live Modal deployment

   owner's own passphrase login) still completes end to end against a
   local run. If a live-Modal deployment isn't reachable this session to
