## A mistake this pass made, and the fix

`gh pr merge 737 --squash` succeeded against a clean MERGEABLE/CLEAN read,
but #737's actual base branch was another PR's branch, not `main` —
`mergeable` is computed against a PR's own base, which said nothing about
whether that base was the trunk. The squash commit landed on a dangling
branch ref and never reached `main`. Caught in the same pass (while
checking #773, which turned out to be stacked the same way) by reading
`baseRefName` on every PR already merged. Fixed by cherry-picking the
squash commit onto a fresh branch off current `main`, resolving the four
resulting conflicts (two registers by date, one shared dict key in
`tools/board.py` by taking the union of both additions, one test file by
keeping both appended blocks), reconfirming `tests/test_board.py` (144
passed), and folding the result into this run's own branch rather than
opening a second pull request, since this run is bound to ship exactly
one. Full writeup, with the general remedy, in
`docs/agents/incidents.md` under
`INC-2026-11-09-gh-pr-merge-landed-a-squash-on-a-stacked-prs-real-base-not-on-main`.
Re-verified `baseRefName` on every PR merged after this point.
