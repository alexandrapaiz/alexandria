### 2. The open sql_query finding now reaches a capability, not just data (carried, widened, owner action unchanged)

The 2026-10-01 audit's finding 2 is still open and is unchanged in the code.
`sql_query`'s docstring in `mcp/server.py` still names a closed list of seven
tables and four views, and the code still enforces no table restriction: the
guard is a prefix match on `select` or `with` plus a refusal of embedded
semicolons. Re-read this run at `mcp/server.py:248`. `subscribers` and `users`
are still in the same database and still readable.

What changed is the table, not the tool. **`subscribers` gained
`unsubscribe_token uuid` with a unique index since the last sweep.** That
column is a bearer capability by design, and `site/lib/unsubscribe-core.js`
explains why in its own header: the emailed link carries a token rather than an
address so that knowing somebody's email grants nothing. The necessary other
half is that holding the token grants what the token is for. A `POST` to
`/api/unsubscribe` carrying one unsubscribes that row with no session.

So the exposure behind one compromised MCP token has changed shape. On
2026-10-01 it was disclosure, meaning the list's names and addresses. It is now
disclosure plus the ability to unsubscribe the entire list in a single pass,
with nothing in the product's own records to distinguish that from readers
leaving on their own. Disclosure is bad and it is reversible. Mass
unsubscription is not.

Stated so this is not read as worse than it is: the door is exactly as hard to
open as it was. Reaching any of this still needs a bearer token on `/mcp`,
which still needs the owner's throttled passphrase. The write boundary is still
sound, because `set transaction read only` is what enforces it and it catches
the `with ... insert ... returning` form the prefix check lets through. What
grew is what is behind the door.

**The owner's action is unchanged and still the cheap one.** A Neon role for
the MCP server with no `select` on `subscribers` and `users`. No code, no new
dependency, no deploy of ours, and it now closes more than it did when it was
proposed. Re-filed as `urgent` in the ledger with the widened blast radius
written down.

### The MCP server

**The two fixes from 2026-10-01 are on main and correct.** Re-read rather than
assumed. `read_access_token` in `mcp/oauth_flow.py:711` now asks the ledger
whether the session is revoked before returning claims, which closes the 24-hour

`sql_query` is unchanged and is finding 2 above.

**The new payment surface was the main new reading this sweep, and it is good
work.** `site/app/api/polar-webhook/route.js` plus `site/lib/polar-core.js` are
the only thing in the product that learns anybody paid. Every property worth
having is there:

- The HMAC is computed over `await request.text()`, the raw bytes, before
  anything parses them, so an honest caller's whitespace and key order survive.
- A missing `POLAR_WEBHOOK_SECRET` refuses rather than opens.
- All three signature headers are required before any arithmetic.
- The timestamp is checked against a 300-second tolerance **before** the HMAC is
  computed, so a stale replay costs no hashing.
- `constantTimeEqual` is correct: it folds the length difference into the
  accumulator and reads past the end as zero, so it does not short-circuit and
  does not leak length through timing.
- Every `v1` candidate is tried, so a secret rotation needs no flag day, and
  unknown versions are dropped rather than treated as opaque matches.
- The 401 says `invalid signature` and nothing else. The reason, which would
  describe the state of the secret or the freshness window, goes to the server
  log only.
- An unrecognised subscription status closes the door and logs the vocabulary
  gap, rather than leaving access as it was.

One property it does not have, recorded rather than filed: there is no replay
cache, so a captured delivery can be re-sent inside the 300-second window. Not a
finding today, because every handled event writes entitlement state derived from
that event's own status, which makes a replay idempotent in effect. It stops
being idempotent the first time a handler counts something, which is why it is
written down.

Error messages elsewhere: the `db()` DSN echo from 2026-10-01 is unchanged and
remains a `proposed` ledger entry.
