## Severe findings

### 1. Every seat run now publishes its full verbatim transcript on a public repository

Commit `ef2da2e`, merged today, added an upload step to all twelve seat
workflows:

```yaml
- name: Upload run transcript
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: transcript-${{ github.run_id }}
    path: ${{ runner.temp }}/claude-execution-output.json
    retention-days: 90
```

The intent is good and it answers a real problem. Incident 3 and incident 8 are
both about runs whose evidence died with the sandbox, and the 2026-09-18 audit
had to reconstruct a six-failure day from commit timestamps because Actions logs
keep only the init block and the final result JSON. A transcript is exactly what
was missing.

What went with it is the exposure. Three facts compose.

**This repository is public.** Confirmed: `visibility: PUBLIC`, issues enabled,
zero forks. On a public repository, workflow artifacts are reachable by any
actor that can read the repository, which is everyone. They are not a private
channel and they are not the owner's channel.

**The transcript is verbatim, not a summary.** Each file is a JSON list of the
whole run. The engineer's transcript from this morning holds 451 records, of
which 122 are assistant turns and 64 are recorded tool results carrying the
output of the command that produced them. Whatever an agent's tools printed is
in the file, in full.

**GitHub's secret masking does not reach it.** Masking is applied to the job's
log stream. This transcript is written by the action to a file under
`runner.temp` and handed to `upload-artifact` as a file, so the log stream is
never in the path. None of the three published transcripts contains a single
`***` mask marker, which is consistent with nothing on that path being masked.

Put together: any agent that runs `env`, `printenv`, `git remote -v`, or
`cat .git/config` writes that output verbatim into a file that anyone can
download for ninety days. Every one of those commands is permitted, because
runs use `--permission-mode bypassPermissions`, and none of them is forbidden,
because no charter carries a rule about it. The 2026-09-18 audit had already
recorded that `git remote -v` prints the live checkout token into an agent's
own output. That finding was a note about an agent's log. It is now a note
about a published file.

**Scanned, not assumed.** All three artifacts that exist today were downloaded
and scanned against twenty pattern classes, including provider keys, GitHub
tokens in every prefix, Postgres and Neon connection strings, private key
blocks, JWTs, Slack webhooks, and direct `NAME=` dumps of each of the six
secrets these workflows inject. **Zero secret values.** The only matches were
twenty occurrences of the string `GMAIL_APP_PASSWORD` in one transcript, and
each one is the variable's name inside the docstring of `pipeline/weekly.py`,
which that run had read. None is followed by a value-shaped token.

So this is an exposure path and not a breach. The control is what is missing,
not the discipline that has held so far.

**The owner's action.** This needs a decision, and the default of leaving it is
the one option that gets worse with time, because the ninety-day window fills
up with runs nobody scanned. Three ways to close it, and the recommendation is
the first plus the third:

1. Add a redaction step between the action and the upload, so the file is
   filtered before it becomes an artifact rather than after.
2. Or drop `retention-days` sharply, to something like 7, which narrows the
   window without closing it.
3. And add one line to every charter saying that no agent prints the value of
   an environment variable, and that `git remote -v` in particular is never
   run.

Options 1 and 2 are workflow edits, which no agent token can push (incident
12). They need the owner's own push or a PAT carrying the `workflow` scope.
Option 3 is a charter edit, which is outside this seat's surface, so it is
filed for the owner in `docs/ideas.md`.

### 2. The MCP passphrase can be guessed without limit

`POST /authorize` applies no rate limit, no delay, and no lockout. Verified
against the real handler in-process: forty consecutive wrong passphrases
returned forty 401s and nothing else. The comparison itself is right, because
`hmac.compare_digest` is constant-time. The gap is that there is no cost to
being wrong.

That single passphrase is the whole gate. Behind it sit the corpus database
through `sql_query`, a GitHub token that opens pull requests through
`propose_skill` and `propose_change`, and a 180-day refresh token. `/register`
is open dynamic registration, so an attacker can register their own client and
reach the passphrase form legitimately, which means the redirect-URI check
correctly built in run 2 does not stand between them and this.

**This is the second audit in a row to report it.** It was in the 2026-09-18
report and it is unchanged. It was not fixed here because a limiter changes
behavior, it can lock the owner out of her own connector, and where the counter
lives on a Modal container that scales to zero is a design question rather than
a small safe fix. Filed `urgent` for the engineer with the shape recommended
below.

## The prompt injection surface, which grew today

The 2026-09-18 audit's conclusion was that the repository offered nothing for an
injected instruction to exfiltrate. That stopped being true when all eleven
workflows gained `PROJECTS_TOKEN`. Today it moved again, further.

### The PM seat can now start other seats' runs

Commit `2ae2650` activated §5 of the PM charter and §11 of
`docs/standards/pm.md`. The PM workflow gained `actions: write`, and the
mechanism is `gh workflow run agent-<seat>.yml -f owner_instructions='…'` using
the run's own `GITHUB_TOKEN`.

The chain that matters runs like this. The standup reads `gh pr list --state
open` and recent run logs, per §11.2. From what it reads, it composes an
`owner_instructions` string. That string lands verbatim in the dispatched
seat's prompt under the heading "Owner instructions for this dispatch, binding
for this run and extending the charter." The dispatched seat then runs with
`bypassPermissions`, `contents: write`, `pull-requests: write`, and
`PROJECTS_TOKEN` in its environment.

Anyone can open a pull request on a public repository. Text in a title or a body
is content a stranger writes and the PM reads. Nothing in the path marks it as
data rather than instruction, and at the far end it arrives wearing the owner's
authority.

**What holds today.** The structural control is real and it is the repository
variable `PM_DISPATCH_ENABLED`, which must be exactly `true`, which only the
owner can set, and which no seat can change. §11.4 adds ceilings, a rule that
every decision inside an instruction must already exist in a file and be cited,
and a rule against dispatching while the owner is present. The observed history
is clean: zero issues have ever been opened here, there are no forks, and all
85 pull requests to date came from the owner or from her own app.

**What does not hold.** Those criteria are prompt-level guardrails against a
prompt-level attack. They constrain a cooperative PM and they are not evidence
about a subverted one. And the gap the last audit proposed closing is still
open: of twelve charters in `prompts/`, **zero** carry any rule about untrusted
content. The only file in the repository that mentions the idea is this seat's
own charter, and it mentions it as a duty to audit rather than as a rule that
binds a reader.

**One question for the owner, which this seat cannot answer.** Is
`PM_DISPATCH_ENABLED` set? `gh variable list` returns 403 to this run's token,
which is correct least-privilege behavior and also means the audit cannot tell
whether the mechanism is live. If it is set to `true`, the recommendation is to
unset it until a charter paragraph about stranger-authored text exists, because
the paragraph is a day of work and the mechanism is already armed.

### The MCP server can propose a rewrite of any charter

`propose_change` accepts any path matching `^(prompts/[a-z0-9_-]+\.md|sources\.yaml)$`.
That regex is correctly anchored and it permits no traversal. It also matches
every seat charter in the repository, including `prompts/security-agent.md`.

So a holder of an MCP access token can open a pull request that rewrites any
agent's charter, with the title `meta: prompts/pm-agent.md` and the body "Proposed
by the alexandria meta-review", which is what a routine proposal looks like. The
human merge is a real gate and it is the reason this is not severe. It sits here
because it composes with the finding above: the org's own rules tell seats to
read open pull requests, and a charter rewrite is the one diff that would change
what every later run does.

Recommended narrowing, which preserves the tool's purpose: exclude
`prompts/*-agent.md` from the pattern, since charters are the owner's by the
same rule that governs every seat. The generator prompts that meta-review
actually exists to improve are untouched by that change.

### What is clean

**No script injection.** `inputs.owner_instructions` appears in sixteen places
across the twelve workflows, and every one of them is inside a `prompt:` block.
It never reaches a `run:` block, so it never reaches a shell. Checked
mechanically, not by eye.

**No hostile trigger.** All twelve seat workflows fire on `schedule` and
`workflow_dispatch` only. There is no `pull_request`, no `pull_request_target`,
no `issue_comment`, and no `workflow_run`. `workflow_dispatch` requires repository
write, so an outsider cannot start a run at all.

## The MCP server

Two findings above are the server's. Three more sit here, and four things were
fixed in this run.

### Authorization codes are replayable for their full ten minutes

Verified: one code was exchanged at `/token` three times in a row and returned
three valid access and refresh token pairs. OAuth 2.1 §4.1.2 requires that an
authorization code be single-use and that the server revoke previously issued
tokens when one is replayed. Neither happens, because `read_token` checks the
signature, the expiry, and the `typ` claim, and there is nowhere for a used code
to be remembered.

The cause is the stateless design, which is otherwise the right call and is what
makes the redirect-URI check testable on a laptop. The honest position is that
this cannot be fully closed without somewhere to keep state. Ranked options:

- Cut the code TTL from 600 seconds to 60. A legitimate exchange happens in
  under a second, so this costs nothing and shrinks the window tenfold. It is
  the one-line version.
- Keep a set of consumed code identifiers in the container's memory. It catches
  the common case and it is imperfect across cold starts and replicas, which
  should be written down next to it rather than discovered later.
- Store codes in Postgres, which is the correct fix and is a day of work.

Practical severity is moderate rather than high, because an attacker holding the
code also needs the matching `code_verifier`, and PKCE is enforced correctly.

### The metadata endpoints reflect the Host header

`base_url()` built the issuer and every advertised endpoint from
`request.headers['host']`. Verified: a request carrying `Host: attacker.example`
came back with `"token_endpoint": "https://attacker.example/token"`. A client
that fetched discovery through any path where the Host can be influenced would
send its authorization code and its `code_verifier` to whatever host that
document named.

This run fixed the crash half of it, which is that indexing the header turned a
request without one into a 500. Who gets to choose the value is still open,
because the fix is to pin the public host and that means a new environment
variable on the Modal app, which is a runtime change under
`docs/agents/runtime-changes.md` and belongs to the engineer with a smoke test.
Filed.

### rag_answer carries incident 24's failure class

`RAG_MODEL = "openai/gpt-oss-120b"` is a hardcoded free-tier Groq model with no
availability check, which is the exact shape of incident 24, where the press
stopped printing because `groq/compound` began returning 404. The engineer is
already dispatched on the press in PR #75, and the point of recording it here is
that the standing fix incident 24 calls for, an availability check and an
ordered fallback list, needs to cover `mcp/server.py` and not only
`pipeline/`. Otherwise the MCP server is the next thing to fail this way.

The server does degrade better than the press did. `rag_answer` catches
`httpx.HTTPStatusError` and returns `{"error": "synthesis model unavailable:
404"}`, so a caller is told. Two gaps in that handler: `call_groq` parses the
response with `json.loads` and a `json.JSONDecodeError` is uncaught, and
`httpx.TimeoutException` is uncaught. Both surface as a 500 through MCP rather
than as a message. Small, and filed rather than fixed, because the right fix is
one error path for the whole family and that is the engineer's availability work.

### What holds

`sql_query` is layered correctly and the layering is what makes it hold. The
single-statement check rejects any `;` in the cleaned string and requires the
statement to begin with `select` or `with`, which is conservative to the point
of refusing legitimate dollar-quoted queries. Behind that, `set transaction read
only` is the real stop, because it defeats a data-modifying CTE that slipped
past a regex, and `set local statement_timeout = 15000` bounds the cost. The
200-row `fetchmany` bounds the response.

The JWT handling is sound. `algorithms=["HS256"]` pins the algorithm, so the
`alg: none` and RS-to-HS confusion attacks do not apply, and every token carries
and is checked for a `typ` claim, so an access token cannot be presented as a
refresh token or as a code.

The stateless client registration does what its docstring claims. The
`client_id` is an HMAC over the registered redirect URIs, the comparison is
`hmac.compare_digest`, and the redirect URI is checked at three points: before
the passphrase form is drawn, again on the post because hidden fields are the
attacker's to rewrite, and a third time at `/token`. The refusal renders in
place rather than redirecting, which is the right choice and the comment says
why.

### Fixed in this run

- **`state` went into the authorize redirect unencoded.** A state of
  `a&scope=admin` arrived at the client's callback as a parameter the client
  never asked for, and one containing `#` truncated the rest of the query into
  a fragment the client's server never sees. Verified before and after. It is
  percent-encoded now, the JWT in `code` is byte-identical because its alphabet
  was already URL-safe, and three parametrized tests hold the line.
- **`request.headers['host']` is now `.get`**, in `mcp/oauth_flow.py` and in the
  bearer guard in `mcp/server.py`. A request with no Host header was a 500.
- **`python-multipart` is now declared in the image.** Every OAuth endpoint is
  built on FastAPI's `Form(...)`, which raises at request time without it, and
  it reached the image only as a transitive dependency of `mcp` by way of
  `fastmcp`. An upstream resolver change would have broken `/token` and
  `/authorize` with no warning and no way to see it coming.

## Supply chain

### The agent image is pulled by a mutable tag

`agent-engineer.yml` and `agent-frontend.yml` both run in
`ghcr.io/alexandrapaiz/alexandria-agent:latest`. Whatever that tag points to at
cron time is what executes with `bypassPermissions` and every secret those two
seats carry. `build-agent-image.yml` moves the tag on any push to main under
`.github/docker/**`, so a bad build becomes both seats' runtime with no step in
between. The other ten seats run on the bare runner and are not affected.

Pinning by digest is the fix and it is a workflow edit, so it is the owner's
push. It also needs a deliberate process for moving the digest, because an
unmovable pin is its own failure mode. Filed rather than proposed as a
one-liner.

Actions are still pinned by mutable tag, `actions/checkout@v4` and
`anthropics/claude-code-action@v1`. Same class, same blocker, reported in both
previous audits and unchanged.

### Nothing verifies the vendored third-party skills

`skills-lock.json` records a `computedHash` for each of the twenty-one Clerk
skills vendored under `.agents/skills/`, which `.claude/skills/` symlinks into
the agent's context. A hash file is a good instinct and the register is the
right shape.

**Nothing reads it.** A repository-wide search for the string `skills-lock`
outside `.git` returns the file itself and no consumer. The hashes are produced
by the upstream installer and this audit could not reproduce one from the
vendored bytes, so this is not a claim that any file was tampered with. It is a
narrower and more certain claim: third-party markdown that goes into every
agent's context on every run has a manifest and no verification step, so the
manifest cannot currently detect anything.

## One thing this run could not check

Whether `PM_DISPATCH_ENABLED` is set. `gh variable list` returns 403 to this
run's token. That is the least-privilege posture working as intended, and it is
also the single fact that decides whether finding 3 is armed or dormant. It is
