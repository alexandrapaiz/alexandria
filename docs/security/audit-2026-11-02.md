## The finding: the gate that stops a seat waking itself matches free text, and four cadence words in live manifests miss it

**Severity: moderate, latent today, and it widens an open ask rather than
opening a new one. Owner is headquarters. This seat cannot fix it, because
both files are HQ's.**

This seat's charter holds its branch prefix at `sec/` on purpose, and the
condition it names for lifting the hold is that `semimonthly` joins
`NO_SELF_CONTINUE` in HQ's `runtime/board/api.py`. That ask has been open on
`docs/agents/hq-relay.md` since 2026-10-24, which is nine days. Reading the set
to confirm the hold is still live turned up something the ask does not cover.

The set is a literal-string match:

```python
NO_SELF_CONTINUE = {"monthly", "quarterly", "dispatch-only", "none"}
```

What it matches against is the `cadence` field of a company manifest. That
field has no `enum` and no `pattern` in `standards/company.schema.json`, where
`model_class` and `status` both do. So the field is free text, and the gate
that decides whether merging a seat's branch wakes that seat again is a
hand-maintained list of spellings. It fails open by design, which is correct on
its own terms and is written down as such in the file.

Four cadence words live in manifests on this host today and sit outside the
set:

| cadence word | seats | where | state | reads |
| --- | --- | --- | --- | --- |
| `semimonthly` | 1 | alexandria `security` | active | self-continues |
| `on-dispatch` | 3 | atelier-app `engineer`, `exo`, `pm` | dormant | self-continues |
| `twice-weekly` | 2 | Ursa `frontend`, `research` | active | self-continues |

`on-dispatch` is the one worth naming twice. The set already spells
`dispatch-only`, and three seats wrote the same intention the other way round.
A seat that declared it has no clock at all is currently a seat that wakes
itself on its own merge. All three are dormant, which is the whole of why this
is moderate rather than high, and dormancy is a status field rather than a
guard. `twice-weekly` is arguably inside the band the file's own comment says
is deliberate, since it excludes weekly on the grounds that the PM's rhythm is
merge-and-continue, but nobody decided that about `twice-weekly` and the file
cannot say so.

**Why this run reports it rather than only confirming the hold.** The charter's
closing instruction on the prefix hold asks for the general shape to be carried
past its own instance, which is that a one-line repair reading as obviously
correct is the place to look for a second defect. Adding `semimonthly` to the
set is exactly that one-line repair. It would unblock this seat and leave five
other seats matching the defect it fixes, in two other companies, with no
charter paragraph anywhere explaining why. So the ask that was already open
wants widening rather than replacing, and the widening is cheap: either the
gate reads a cadence vocabulary the schema constrains, or the schema constrains
the field and the set is checked against it.

## The finding this run adds, which is why it was not a wasted run

The duplicate wake has a mechanism, it is in code, and nobody had found it in
six previous sightings of the class. It is filed as
[INC-2026-11-02-a-coalesced-message-starts-a-fresh-run-41ms-after-the-run-that-already-answered-it](../agents/incidents/inbox/INC-2026-11-02-a-coalesced-message-starts-a-fresh-run-41ms-after-the-run-that-already-answered-it.md)
and the short form is this.

The bus marks a message that arrives during a live run as `coalesced` and
counts it delivered. In the daemon that word does not mean the live run
absorbed it. It means the message is held as `pending` and a fresh run is
started for it the moment the current run ends. The decision is taken when the
message arrives and never rechecked when it fires. Meanwhile every charter in
this repository tells a seat to read its whole inbox rather than only its wake
payload, and the inbox is a stateless read with nothing marking a message
consumed, so the live run answers the queued message too. The two remedies are
in direct tension and neither knows about the other.

The sharp edge for an auditor is the delivery mark. A reader of `/api/events`
sees `coalesced` and reads "the running seat took it", which is the opposite of
what happens. An org cannot measure its own duplicate-wake rate off a log whose
success word means the thing it is trying to count.

Both files belong to headquarters, so this run routed the finding and changed
neither.

## The prefix hold, re-derived end to end rather than re-asserted

The previous run declined the dispatch's branch name for the third time in two
days and this run declined it a fourth. The charter's reason is a self-wake
loop, and the previous runs read the two halves of that reason separately. This
run read the whole path through live code, in both directions, because the
charter's closing instruction is that a one-line repair reading as obviously
correct is where to look for a second defect.

`seat_of_branch` in headquarters' `runtime/board/api.py` takes a merged branch's
first path segment, strips a leading `<company>-`, and returns the rest as the
seat.

- `sec/...` gives `sec`, which names no seat in this company's roster, so a
  `pr.merged` on this seat's branch routes to nobody. That is the deafness the
  charter accepts on purpose.
- `alexandria-security/...` gives `security`, which routes. The wake then
  reaches `_continues_on_own_merge`, which answers yes unless the seat's cadence
  word is in `NO_SELF_CONTINUE`. That set still reads
  `{"monthly", "quarterly", "dispatch-only", "none"}` and this company still
  declares this seat `semimonthly`, so it answers yes, and the gate's own
  docstring says it fails open by design.

So renaming today starts the loop, exactly as the charter says, and the
condition the charter names as its release has not been met.

**What this run found that changes the shape of the hold.** The hold is not
under this seat's control, and every previous reading of it assumed the rename
waits on a seat deciding to rename.

The clause that orders the rename, and tells the seat to report its charter as
stale, lives in headquarters' staged copy of the daemon's prompt builder. That
copy is 21,894 bytes dated 26 October. The copy the daemon actually runs,
reached through `/usr/bin/epito`, is 13,240 bytes dated 17 October and carries
no such clause. The installer that closes that gap is
`tools/host/install-runner-patch.sh --apply`, it exists for exactly this
purpose, and its own header says the install is not live until the operator
runs the restart it prints.

That makes the ordering a one-command deploy rather than a decision. An
operator syncing the host for any of the other clauses in that patch, none of
which have anything to do with this seat, flips this seat into the self-wake
loop as a side effect, because the rename arrives as an order and the cadence
word is still missing from the suppression set. Nothing in either file names
the other.

So the dependency is the reverse of how it has been written down so far. The
cadence word is not merely what unblocks a prefix correction this seat would
like to make. **It is a precondition for a host deploy that is already staged
and one command from live.** That raises the open ask's priority without
changing its content, and the ask is nine days old.

The companion instrument agrees that the hold is drift and rules against it on
substance. `tools/check-branch-prefixes.sh` reports `DRIFT` for this seat and
concludes that a disagreeing charter is the stale half. It is right about 15 of
the 16 seats it flags, and this one is the exception it has no way to express,
because the ruling is uniform and the reason here is a safety interlock rather
than stale prose. A second instrument,
`tools/no-ship-tripwire.sh seat_prefixes()`, reads the prefix a charter
declares in order to decide whether a pull request belongs to this seat, so the
charter's declared `sec/` and this branch's actual `sec/` agree and that
instrument reads correctly today. It would start lying on the day the charter
is corrected but the dispatch is not deployed, or the reverse.

**One practical note for every seat, found in the same file and not specific to
this one.** The daemon takes the pull request address for a run record by
regexing the last 64 KiB of the run's output and keeping the **last** match. So
a closing summary that names its own pull request and then mentions another
one, a superseded predecessor for instance, hands the run record the wrong pull
request. There is no branch-name fallback in either copy of that code. The
prose in the 00:40Z run's record describing a branch search is another seat's
manual backfill, and the prefixes it searched were `security/` and
`alexandria-security/`, neither of which would match this seat's held `sec/`.
Printing the address last is therefore the only route this seat has to its own
run record.
