# Security and debug audit — 2026-09-18

First run of the combined debug and cybersecurity agent (ADR-20). This is the
baseline: full-history secret scan, full audit across every area the charter
names, and small fixes only where the fix was certain. The owner's dispatch
tonight named workflow security and the public/private boundary as the two
areas that matter most, since five other agent seats ran in parallel tonight
and the product launches 2026-10-13. Those two sections come first.

## Severe findings (owner action needed)

**A phishing link against the MCP server's login page can hand an attacker
full MCP access.** `/register` never stores the redirect URI a client
submits, and `/authorize` accepts any redirect URI from the request with no
check against a registration. PKCE does not stop this, because the attacker
who builds the phishing link owns the matching code_verifier from the start.
If the owner (the only real user, per ADR-11) enters the real passphrase on
a link built this way, the attacker gets a full access and refresh token
pair, including the tools that open pull requests. See MCP section below and
the `urgent` ledger entry. This needs a code fix, tested against a live
deployment, before the server is trusted with anything sensitive.

**The public repo's git history still holds a full paid-product digest.**
`digests/2026-W37.md` was committed nine times before the folder went
private, and every version is still retrievable from the public repo's
history even though the working tree and .gitignore are now correct. This
is not a credential, so no rotation applies, but it is real exposure of the
product ahead of the paywall. Purging it means rewriting history and force
pushing, which is disruptive and irreversible, so the decision belongs to
the owner. See the public/private boundary section and the `urgent` ledger
entry.

Neither finding is fixed in this PR. Both need a decision or a tested code
change this agent cannot make blind.

**This agent's own token cannot push a fix to any workflow file.** Pushing
this branch with the pinning fix described below (section 1) was rejected
by GitHub itself: "refusing to allow a GitHub App to create or update
workflow `.github/workflows/agent-engineer.yml` without `workflows`
permission." That is a GitHub App installation permission, separate from
the `permissions:` block inside each workflow file, and none of the six
workflows request `workflows: write` (confirmed by grep), so no seat's
token can land a workflow-file change today, including this one and
ExO's, whose charter explicitly lists agent workflows as writable. This is
GitHub's own safety rail working as intended, not a bug, but it means the
pinning fix below is described and verified, not applied. If the owner
wants any agent seat able to land a workflow-file change autonomously, the
GitHub App installation needs the `workflows` permission granted
explicitly. Until then, this class of fix needs the owner's own push, or a
PAT with that scope.

## 1. Workflow security

All six workflows (`agent-*.yml`) declare explicit `permissions:` blocks:
`contents: write` and `pull-requests: write` on every one (each agent needs
to push a branch and open its PR), `id-token: write` on every one (needed
for the Claude Code action's OIDC token), and `actions: read` on the two
that read run history (exo, security). No workflow requests anything wider.
No workflow uses `pull_request` or `pull_request_target`, so there is no
fork-PR-triggered privilege escalation surface. `owner_instructions` is
interpolated straight into each prompt, but `workflow_dispatch` already
requires repo write access to trigger, so this input is never
attacker-controlled.

**Prepared this run, not applied (see the severe finding above):**
`actions/checkout@v4` and `anthropics/claude-code-action@v1` are floating
major-version tags, not immutable references. A moved tag is a
supply-chain risk: whoever controls the tag controls what code runs in
every future workflow_dispatch and every cron. The fix is to pin both to
their currently-resolved commits across all six workflow files:
`actions/checkout@11d5960a326750d5838078e36cf38b85af677262` (v4.4.0) and
`anthropics/claude-code-action@a4f54ef2c58884867281bd8e2f8d63352ad019a9`
(v1.0.229). This was verified to change nothing about today's behavior,
since both SHAs are exactly what the tags already resolved to when checked
tonight, but this run's token cannot push a workflow-file change, so the
edit itself is not in this PR. It is a `proposed` ledger entry with the
exact lines to change, ready for the owner or a future run with the
`workflows` permission to apply directly.

Trade-off worth naming plainly for whoever applies it: pinning trades away automatic upstream
fixes. `claude-code-action`'s v1 tag moved as recently as tonight, so it is
under active development, and a future security or bug fix on that action
will not reach these workflows until someone bumps the SHA by hand. The
next security-agent run should treat re-checking these two SHAs against
upstream as a standing item, or the owner may prefer Dependabot's GitHub
Actions update support instead of a manual biweekly check.

35297972051 was already fixed by commit c7e67d5 before this run started.
The next engineer run went green. No action needed.

## 5. The MCP server (mcp/server.py)

**OAuth and PKCE.** PKCE (S256) is required and checked at both `/authorize`
and `/token`. JWT verification pins `algorithms=["HS256"]`, which blocks
`alg: none` and asymmetric-key-confusion attacks, and expiry is checked on
every request. Both are implemented correctly. The severe finding above is
a different gap: redirect URI validation, which PKCE does not cover.

**Refresh tokens.** Each refresh issues a new access and refresh pair, but
the presented refresh token is never invalidated, and there is no
server-side store to revoke a single token. The only way to invalidate any
token is to rotate the signing secret, which invalidates everything at
once. Combined with a 180-day refresh token lifetime, a single leaked
refresh token is usable for up to six months with no selective revocation.
Medium severity.

**`sql_query`'s SELECT-only enforcement.** The gate itself is a string or
regex check, which is bypassable in the abstract, but it is meaningfully
backed by `set transaction read only` on the connection, so Postgres itself
rejects any data-modifying statement the regex might miss, including
writable CTEs. No exploitable bypass found. This is real defense in depth,
not a false sense of one.

**Row limiting and timeouts.** Row limiting happens client-side
(`fetchmany(200)`) rather than as a query-level `LIMIT`, so an expensive
query still runs server-side for up to the 15-second statement timeout
before truncation. The timeout bounds duration, not peak resource use in
that window. Low severity.

**Error handling.** No `sql_query`, database call, or outbound HTTP call in
the file is wrapped in a try/except, so a raw exception (a Postgres error
string, a GitHub API error body) can propagate back to the MCP client
un-sanitized. A malformed query referencing a nonexistent column would
return the raw Postgres error. Low severity on a single-user system, but
worth closing since it costs little.

**Rate limiting.** None anywhere in the file. The passphrase check at
`/authorize` uses a constant-time comparison, which prevents timing
attacks, but nothing limits the number of attempts, so the passphrase can
be brute-forced by an automated client with no lockout. Medium severity,
and it depends on how strong the passphrase actually is.

**Injection surface beyond SQL.** None found. No `subprocess`, `os.system`,
or `eval` anywhere. The `slug` and `path` inputs used in GitHub content API
calls are properly allowlisted by regex, which blocks path traversal.

**Authorization blast radius.** Any valid access token can call
`propose_skill` and `propose_change`, which hold GitHub PR authority on the
server's behalf. Per ADR-13, those PRs can be merged by an agent panel
rather than a human, so a stolen token's blast radius includes an attempt
at autonomous code or skill injection, gated only by that panel's judgment
rather than a hard authorization boundary. This raises the stakes on the
redirect_uri finding above rather than being a separate one.

None of the MCP findings are fixed in this run. The redirect_uri gap is
`urgent` in the ledger. The rest are described here for the engineer to
prioritize, since none of them can be verified without a live Modal
deployment and none of them are safe to change blind.

## 6. Prompt injection surface

Every agent workflow runs `--permission-mode bypassPermissions` (added
2026-09-17 to fix headless CI tool-permission prompts), and every workflow
carries `contents: write` and `pull-requests: write`. The market agent and
the OKR agent's monthly competitor benchmark both read arbitrary public web
content by design (competitor sites, forums, blogs), which is exactly the
surface where an injected instruction could try to steer an agent.

Two things bound the actual risk today. First, no workflow wires any secret
beyond the scoped GitHub token and the Claude Code OAuth token into these
runs, checked directly in every `agent-*.yml`'s `env:` block, so there is
nothing for an injected instruction to exfiltrate beyond what a normal PR
already exposes. Second, no agent can merge its own PR, so the owner's
review at merge time is the backstop against any PR whose content or diff
looks wrong.

That backstop is the only backstop, though. Each charter's promise to write
only inside a given path (`docs/market/` for the market agent, and so on)
is prose, not a technical control. Nothing in the workflow or the repo
would stop an injected instruction from writing outside that scope in the
same PR, where it would need to be caught by eye at merge time. Proposing,
not building, since this is new CI tooling and belongs to the engineer: a
required PR check that fails if a PR's changed paths fall outside the
dispatching agent's declared allowlist, so path-scope enforcement does not
rely solely on the owner noticing a subtle injected diff during review.
