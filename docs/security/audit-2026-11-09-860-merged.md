# Security and debug audit, 2026-11-09 (message wake, the merged draft)

This run was woken by a note from the PM seat saying that the draft this seat
finished and readied has been merged, and asking this seat to read its inbox
on the board and reply there with the reason. So this is a close-out wake
rather than the semimonthly sweep, and the scope below is chosen on that
basis. Two long sweeps already ran today on this seat's two previous runs, and
one of those runs was still writing while this one worked, so a third full
pass would have duplicated work rather than added any.

## What this run was asked, and what the inbox actually held

The note is the trigger, and its own account is worth recording because it is
the first time another seat has reread this seat's gates rather than its
report. The PM reran the five gates the merged draft named, on that branch
instead of on the report, and every count matched. It also declined to wait on
the second full-suite pass that draft flagged as still running, on the grounds
that the gates which actually gate this repository were already green, and
that a third long run risked orphaning the draft again. Both judgments look
right from here and neither is contested below.

Reading the inbox turned up something the note did not say. Eighteen messages
are addressed to this seat in this company, and fifteen carry an answered
marker. Three carry none at all, and all three came from the ExO seat between
04:41 and 04:48 this morning. Those three are the only unanswered work in the
inbox, so they are what this run acted on. They are answered on the board as
part of this run, and the substance is below.

said them after running this seat's instrument over three trees rather than

This run verified both by running them rather than by reading that report,

## Finding 2, the ratchet's first verified turn, and the instrument held still

The ExO re-measured main after the reverts and reported 26 unbounded over
fifteen files. This run reads 24 on current main. A count that falls after the
instrument changed in the same pull request that set the baseline is not
evidence of anything, so the two had to be separated before either number
could be used.

The separation was done by running the current instrument against the old
tree, in a worktree at the commit the ExO measured. It reports 26 there and 24
on current main. So the instrument is stable across the two trees, the ExO's 26
reproduces exactly, and the fall to 24 is debt actually paid rather than
detector drift.

Which calls moved is also checkable, and the arithmetic closes. Three were
paid, in `tools/cron_firing.py`, `tools/resolve_register_conflict.py` and
`tools/root_scratch.py`, all three on this seat's own merged work. One was
added, in `tools/merge_register.py`. That is 26 less three plus one, which is
24, and it means the first turn of this ratchet was a net gain of two with a
new debt opened inside it.

## Finding 3, the one call somebody else controls

`tools/merge_register.py` is vendored from headquarters and it is where the
twenty-fourth unbounded call came from. The draft's own docstring predicted
this shape before it happened, which is the useful part: the count this file
exists to drive down went up by one on somebody else's merge, and the only
reason anyone saw it is that a seat ran the suite by hand.

That is this sweep's answer to the supply-chain question in the charter, as far
as this run may answer it. The artifact is `tools/merge_register.py`, the trust
assumption is that an HQ re-vendor carries no new unbounded external call, and
the blast radius is one subprocess call to `git` with no clock, in a tool that
writes a register. A hang there stalls a run and prints nothing while it does,
and the exit the host writes for that is the same word it writes for the
sixty-minute wall.

The rest of the supply-chain row is deliberately not written here. This seat's
other open pull request holds `docs/security/upstreams.md` and was still
committing to it while this run worked, so writing that file from two runs at
once would reproduce the ledger-collision class on purpose. The row is paid
there, and this section names only the artifact that run cannot have seen.

## Finding 6, a docstring that lies, and it is not this seat's file to fix

`tools/answered_by.py` offers a bare invocation and its docstring annotates it
`# this seat, the live board`. The flag underneath defaults to the string
`exo`. So a run of any other seat that follows the docstring audits the ExO
seat's inbox, and the only signal is one seat name in the first line of output,
which a reader skimming for the verdict does not read.

This was found by running it from this seat and getting a report about
somebody else's mail. It is the class the ExO itself reported against a
different checker this morning, which answered about other seats' trees, so it
is that class in the instrument built to measure the mail.

Two reasons it is reported rather than fixed. The file belongs to the ExO seat,
which built it today and carries a standing read against it, so changing the
default would silently change what that standing read measures. And the
charter's rule about an editor rule being a different axis from an authority
tier is the ExO's own lesson from this morning, which would be a strange thing
to acknowledge in a reply and then step over in the same run. So this goes to
that seat on the board instead, and to the ideas inbox for whoever picks it up.

Worth separating from it: the existing census judgment on that same flag is
about which values are valid, not about what the default is, so this is not
already covered by that row.

## Finding 7, a latent misattribution that has not fired

`tools/incidents.py` defaults its `--seat` flag to `engineer`, and that value
is written into the heading of the register entry the tool creates. So any seat
filing without the flag stamps the entry as the engineer's.

This run looked for a live instance rather than reporting the risk on its own.
Of 287 entries in the register's inbox, 145 carry a parseable seat in their
heading, and six of those name a seat different from the commit author. All six
of those authors are the owner's merge identity rather than a seat, so all six
headings are correct and none is a misattribution. So the finding is latent,
the severity is low, and the honest form of it is that the default happens to
match the seat that files most often.

One observation beside it, not a finding. The other 142 entries carry no seat
in the shape the tool's own skeleton writes, so anything keying on that heading
format reads about half the register.

## Finding 8, message routing integrity, measured by using it

The board marks a message answered by joining it to its addressee's next
outbound letter, whatever either one says. This run's own trigger arrived
already marked answered by a reply sent ten minutes later about an unrelated
spec clause, which is the fourth instance of a class the register already
carries three entries for. It is filed this run at
`INC-2026-11-09-the-clock-join-marked-this-runs-own-trigger-answered-and-the-label-this-seat-shipped-is-what-caught-it`.

Two things in it are new and both were measured rather than reasoned. The
first is that the label this seat shipped for this class caught the instance
out loud, which is its first live confirmation. The second is what happened
when this run wrote an explicit link into all four of its replies. One marker
became the first verified one in this seat's inbox. The other three show the
clock winning anyway, including the trigger note, whose correct reply exists on
the bus and is unreachable from the message it answers.

Why it is in a security audit rather than only a register. The inbox is the
surface every charter orders a run to read before acting, and the suppression
being asked for upstream would key on this marker. Keyed on it as it behaves
today, this wake would have been suppressed and the three genuinely unanswered
letters would have been dropped. So the ask is no longer for a field, which now
exists, but for the join to prefer the link when a sender wrote one. That is
routed to the ExO seat on the board, which owns both the relay and the open row
for it, rather than written into the relay file from here, because that file is
being edited by this seat's other live run.
