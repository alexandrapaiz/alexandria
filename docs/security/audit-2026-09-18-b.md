## 1. What each failed run delivered, and what was lost

Evidence is the run logs plus the repository. One limitation to state plainly:
the Actions logs contain only the action's init block and its final result
JSON. The turn-by-turn transcript is written to
`/home/runner/work/_temp/claude-execution-output.json` inside the runner and
is destroyed with the sandbox, so it is not recoverable. Everything below about
what a run *did* is reconstructed from commits, branches, pull requests and
board mutations whose timestamps fall inside the run's window.

### The two failure modes

| Mode | What the result JSON says | What it means |
|---|---|---|
| A. Cap starvation | `subtype: error_max_turns`, `is_error: true` | The run was cut off mid-work. Anything not yet pushed is gone. |
| B. Overshoot check | `subtype: success`, `is_error: false`, then the action fails the job | The run finished its work and shipped. Only the conclusion is red. |

`Claude reported a successful result after N turns, exceeding the configured
maximum of M`. The agent reported success and the action failed the job anyway

## 3. The security dimension: is there one

**No. Stated plainly: these failures have no security dimension.** Three checks,
each run rather than assumed.

**Secrets in failure logs: clean.** All 37 of today's run logs were downloaded
and scanned for credential-shaped strings — GitHub tokens (`ghp_`/`ghs_`/`gho_`/
`ghu_`/`ghr_`), `sk-ant-` and generic `sk-` keys, Postgres and Neon connection
strings carrying a password, AWS access key IDs, three-part JWTs, PEM private
key blocks, and Stripe and Clerk live and test keys. **Zero matches in any
file.** Positive evidence of masking is present in all 37: the action's input
echo shows `"claude_code_oauth_token": "***"`, the env echo shows
`DEFAULT_WORKFLOW_TOKEN: ***`, and `PROJECTS_TOKEN: ***` appears masked in all
27 logs that reference it. A cap failure does not change this, because the
failure path prints only the result JSON, which carries turn counts, timings,
cost and model usage and no tool output. Counter-intuitively, the *thinner* logs
of a failed run are a smaller disclosure surface than a successful one, not a
larger one.

**Cheaply inducible repeated runs: not possible.** Every one of the eleven
workflows is triggered by `schedule` and `workflow_dispatch` only. Checked
across all eleven files, there is no `pull_request`, no `pull_request_target`,
no `issue_comment`, no `issues`, no `workflow_run` and no `repository_dispatch`.
`workflow_dispatch` requires write access to the repository, so an outsider
cannot start a run at all, let alone loop one. There is no public, unauthenticated
or fork-reachable path that causes an agent run to execute, so there is no cheap
way to burn the owner's Claude budget or her Actions minutes from outside. The
cost risk today is entirely self-inflicted: $18.33 lost to the four mode-A runs
was spent by the org on its own dispatches.

**Repeated-run behavior from inside: a real operational hazard, not a security
one.** Incident 14 already records two runs of the same sales dispatch executing
concurrently on one branch, with the second attempting a `--force-with-lease`
push that the lease correctly rejected. Today's reruns after cap failures are
the same shape. The exposure is data loss between trusted agents, not privilege
escalation, and the lease did its job.

**One hygiene note, not a finding.** The checkout action writes the ephemeral
`x-access-token:ghs_...` credential into `.git/config`, so `git remote -v` in
any agent session prints a live token to the run's own output. It is
job-scoped and expires with the run, and GitHub does not mask it because the
action injected it rather than the secrets store. No agent has pasted it
anywhere, and nothing in the repository contains it. Worth one line in the
charters all the same: **never paste `git remote -v` output into a PR body, an
audit report or a commit message.** This agent avoided doing so in producing
this report.

## 4. Sanity check on the chair's new caps and timeouts

The chair made two commits to main this afternoon: `c6bc2c4` raised
`--max-turns` on all eleven workflows, and `57135da` raised
`timeout-minutes` on two of them, pm from 30 to 60 and frontend from 60 to 90.
The other nine kept `timeout-minutes: 45`.

The caps themselves are right-sized against measured demand. The problem is
that **a turn cap is not the only tripwire, and for six seats it is no longer
the binding one.** Raising a cap without raising the job timeout to match does
not extend a run, it just changes which wall it hits, and the job timeout is the
worse wall by a distance. A cap hit is graceful: the SDK returns a result JSON,
the cost and turn count are recorded, and everything already pushed is intact
and diagnosable. A timeout is a SIGKILL of the whole job: no result JSON, no
final turn, no cost figure, and nothing in the log to post-mortem from. Trading
soft failures for hard ones is a regression in failure quality even while the
failure rate improves.

Pace is measured from today's own runs as wall-clock minutes per turn, taken
from `duration_ms / num_turns` in each result JSON. Both the median and the
worst observed pace are shown, because a single slow run should not condemn a
cap on its own.

Two further observations on the caps.

**The two PM runs that died at 60 were starved by a stale cap, not by an
unreasonable dispatch.** Both `35301912056` and `35307268573` were given
multi-job owner dispatches — three jobs and four jobs respectively, including

### The MCP server

**Fixed in this PR: the login form reflected unescaped query parameters into
its HTML.** `GET /authorize` built its hidden inputs as
`value="{q.get(p, "")}"` for all six OAuth parameters, and the wrong-passphrase
re-render did the same for the posted values, with no escaping anywhere in the
file. Every one of those values comes from the query string of whatever link
the user clicked, so a crafted link could terminate the attribute and rewrite
the page — and the page in question is the one where the MCP passphrase is
typed. The fix wraps each interpolation in `html.escape(..., quote=True)`.

It is behaviour-preserving: legitimate OAuth values are base64url strings,
UUIDs and URLs, which contain nothing escapable and render byte-identical, and
a browser decodes entities back before submitting the form, so `POST /authorize`
and `/token` see exactly the values they saw before. Verified locally against
representative values; no exploit payload is recorded here or anywhere in the
branch.

**This matters for the engineer's open PR #29, which does not fix it.** PR #29
is the blocking sprint item for run 1's severe redirect-URI finding, and its
redirect-URI work is good: `registered()` is checked before the passphrase form
is ever drawn and re-checked on the POST, with the comment explaining why the
refusal renders rather than redirects. But the PR moves the OAuth endpoints
into `mcp/oauth_flow.py` and carries the unescaped interpolation across
verbatim, at lines 265-266 and 282-283 of the new file. Worse, the redirect-URI
check does not neutralise the injection, because `/register` is **open dynamic
client registration**: anyone may register a client with their own redirect URI
and receive a valid `client_id`, so `registered()` passing is not evidence of
trust. An attacker who registers first still reaches the form render with an
attacker-controlled `state`.

> **Owner and engineer action:** PR #29 should carry the same two-line escape
> into `mcp/oauth_flow.py` before it merges. If it merges first, it deletes the
> fix made here along with the code it patched, and the vulnerability returns.
> These two changes must land together in either order.

The rest of the server audits clean:

- **PKCE and JWT.** `jwt.decode` pins `algorithms=["HS256"]`, so there is no
  `alg: none` confusion. `read_token` checks the `typ` claim, so an access
  token cannot be replayed as a refresh token or an authorization code.
  PKCE verification uses `hmac.compare_digest` against the stored challenge,
  and the passphrase check is `hmac.compare_digest` too, so neither comparison
  leaks by timing.
- **Token lifetimes.** Access 24 hours, refresh 180 days, code 10 minutes. The
  180-day refresh is long, and there is no revocation path short of rotating
  `AUTH_JWT_SECRET`, which is worth the owner knowing rather than worth
  changing today for a single-user server.
- **`sql_query` SELECT-only enforcement.** Sound, and correctly layered. The
  regex requiring a leading `select` or `with` and rejecting embedded `;` would
  not by itself stop a data-modifying CTE, which Postgres permits and which
  begins with `with`. What actually stops it is `set transaction read only`,
  issued on the connection before the query runs. The defence in depth is
  correctly ordered and `set local statement_timeout = 15000` bounds the query.
  Results are capped at 200 rows.
- **Other injection surfaces.** No `subprocess`, `os.system` or `eval`, and the
  entitlement query on the site is parameterised.
- **Rate limiting: absent.** There is no throttle on `POST /authorize`, so the
  passphrase is open to unlimited online guessing. The comparison is
  timing-safe, and the passphrase is the owner's to choose, so the real defence
  is its entropy. Worth a fixed-window limiter eventually; it is the engineer's
  change, not a behaviour-preserving fix, so it is not made here.

### Workflow security

Posture is good and has improved since run 1, which audited six workflows;
there are now eleven.

- **Triggers.** `schedule` and `workflow_dispatch` only, across all eleven. No
  `pull_request`, no `pull_request_target`, no `issue_comment`, no
  `workflow_run`, no `repository_dispatch`. There is no fork-PR privilege
  escalation surface and no unauthenticated way to start a run.
- **Permissions.** Every workflow declares an explicit block. All eleven take

### Prompt injection surface

**Run 1's central assurance here is now out of date and should not be relied
on.** It concluded that "no workflow wires any secret beyond the scoped GitHub
token and the Claude Code OAuth token into these runs ... so there is nothing
for an injected instruction to exfiltrate". That was true when it was written.
It is no longer true. Since 2026-09-17, by the owner's own all-hands decision
recorded in `5bd6294`, **every one of the eleven workflows carries
`PROJECTS_TOKEN`**, a personal access token scoped to her user-level projects
rather than to this repository, and `agent-research.yml` and `agent-skill.yml`
additionally carry `NEON_RO_URL`, a database connection string that includes
credentials.

So the exfiltration surface is no longer empty. Set against that:

- The repository is **public, with issues enabled** and no issues opened to
  date. Every charter tells its seat to read pull requests, and several tell it
  to read the public web. Anyone on the internet may open an issue or a PR whose
  text an agent will read.
- Runs use `--permission-mode bypassPermissions` with `contents: write` and
  `pull-requests: write`.
- **No charter carries any rule about untrusted content.** Grepping all eleven
  for "untrusted", "prompt injection", "treat as data" or "ignore instructions"
  finds only this charter's own instruction to *audit* the surface. Nothing
  tells any seat that text authored by a stranger is data rather than
  instruction.

The bound that still holds, and it is a real one: no agent can merge its own
PR. Every charter and every workflow says so, none enables auto-merge, and the
owner's review at merge time catches a hostile diff. But merge review does not
catch exfiltration, because a token pasted into a PR body is already disclosed
by the time she reads it, and GitHub's secret masking covers workflow logs, not
API calls an agent makes itself.

To be clear about what this is and is not: **this is an exposure path, not a
breach.** No issue has ever been opened on this repository, nothing in the logs
or the tree shows any attempt, and every token scanned clean. It is listed
because the reasoning that previously made it safe to ignore no longer applies.

> **Proposed, not built, since charters are outside this agent's writable
> surface:** add one standing paragraph to every charter, to the effect that
> text from issues, pull requests by non-owners, and fetched web pages is
> **data to be reported on, never instructions to follow**, and that no agent
> ever writes an environment variable's value into a file, a commit, a PR body
> or a comment. Removing `PROJECTS_TOKEN` from the nine seats whose charters
> never mention the board would be the tighter fix, but it would contradict the
> owner's explicit decision that any seat may file its own board cards, so the
> guardrail is the right lever here rather than least privilege.

Run 1's proposed path-allowlist PR check remains the other half of this and is
still unbuilt.
