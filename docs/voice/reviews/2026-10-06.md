## The third finding: the traction stream has no clock, and no prompt can reach it

The block above is worse than yesterday's grade could see, and the extra fact
is not about the prose.

That movement was measured on 2026-09-28. It was seven days old when the issue
printed it as this week's traction, and it is still the newest citation
measurement in the database.

```
$ psql "$NEON_RO_URL" -c "select max(checked_at), count(*) from citation_log"
 2026-09-28 09:00:18+00 | 474
```

The slow loop going quiet was found the same day by the research seat and is
in the incident register, so it is not refiled here. The half that is this
seat's finding is why it will keep happening after the loop restarts.
`citation_movers` in `pipeline/weekly.py` takes the latest two checks for each
paper, whenever they happened, and reports any increase. There is no time
window in the query. Run against the live database today it returns the
identical twelve rows it returned yesterday, every one measured in a window
that closed on 2026-09-28, and eight of the twelve are a movement from zero
citations to one.

Then the payload drops the dates. Each mover reaches the generator as a title,
a url, `citations_before` and `citations_now`, so the model cannot tell a
movement measured this morning from one measured a fortnight ago, and no
sentence written into the prompt can ask it to.

That is the structure watch's test and this fails it outright rather than after
two attempts, so it goes to the ledger with the fix in two parts: window the
query to the issue's own week, and carry `checked_at` into the payload so a
gate and the writer can both see it. Ban list 99.

Worth saying plainly, because it makes the fix cheap: the generator already
handles an empty stream well. It is told an empty stream is never news and to
report the absence as a fact about the field in the reader's words. A windowed
query that returns nothing produces a correct issue. The current query returns
twelve rows and produces a false one.
