## The single biggest weakness, plainly

**Two rules in `prompts/digest.md` had lost their own opening line, so neither
was a rule any more.** A bullet in that file is a bolded line saying what the
rule is, then a body saying how to obey it. These two were bodies with no
heads, indented, welded to the end of whichever rule came before them.

```
prompts/digest.md:1400   clause inside the item's own prose, not a footnote and not a separate line.
prompts/digest.md:2057   something: every line beginning with `#`, and every run of bold or italic
```

The first is canon law 6, the evidence grade. The second is canon law 12's
final heading gate, which is the last instruction in the file before "Output
the markdown only" and the one that stops the framework's internal names
reaching a reader. That is the ruling the owner has given twice and it is
incident 20.

A model reading the file ran the attribution rule on into "something: every
line beginning with `#`", and ran the count-the-links rule on into "clause
inside the item's own prose". The boundary between one instruction and the next
was gone in both places.

**Both cuts are this seat's own and both were obeying a rule.** `acb4474d` on
2026-09-20 removed four model grades from the evidence rule and took its header
with them. `62b00f2b` on 2026-10-18, titled "five more gates lose the argument
and keep the rule", removed the argument under the heading gate and took its
header too. The canon's weight section tells a run that adds tokens to remove
at least as many, and names what may go: the argument for the rule, the dates,
the account of which print produced which clause. All of those live in the body
of a bullet, one line below the header. The same section says in its own words
that an operative clause never goes.

Thirty-five days and seven days, and every gate built for this file reported
green across both spans, because each asks a question about the file's contents
and none asked whether every rule in it still begins.

## The gate that should have caught it was reading the other direction

`docs/voice/check_voice.py generator` was built two days ago, by this seat, for
this exact class. It reported zero.

Its `truncations` detector reads the line a cut LANDED on, so its first filter
is to skip any line ending in a full stop. A cut that removes a bullet's header
leaves the line before it ending on a full stop, because that line is the end
of the previous rule. The pair is discarded on the first test, every time.

All three of that gate's detectors model one kind of edit, and its own closing
text said so: "an edit that inserted replacement text without removing what it
replaced". Run 43 was looking at an insert, so it built three views of an
insert. Nothing modelled the mirror, which is the edit that removes too much,
and the trimming rule the canon added on 2026-10-18 is what makes that edit
routine.

## Law 14's count could not fail on any artifact the press can produce

`shapes()` counts how many kinds of block an issue carries, which law 14 calls
its first count and says can fail while the other four pass. On 2026-10-06 it
was given `written_here()` so the masthead, the rule and the close would stop
inflating it, and that helper's comment says why in its own words: the count
"used to read 2 on an issue whose generator had added nothing but paragraphs".

The reasoning stopped at page level. The citation line under every item,
mandated twice in the generator as `*title* - [full text](url)` on a line of
its own, is furniture by the same argument, and it is one short line standing
alone, so each one scored as law 14's number-on-a-line device.

```
site/content/issues/2026-W39.md
  shapes 2   paragraph 14  standalone line 5      <- before
  shapes 2   paragraph 14  standalone line 1      <- after, four were citations
```

Every issue has at least one item, so `len(body) < 2` was unreachable by any
artifact. The one condition the command reports on could not fire.

**And the honest half is that fixing it changed no verdict.** Four citations out
leaves one standalone line and the count still reads two. So the law's own
content is asserted beside the count: a list where results are parallel and a
written turn inside a long section are the two devices no furniture can fake,
and the canon describes the reprint she rejected in exactly those words, "no
list, no subheading inside any section, one shape". 2026-W39 has neither. Run
49 reached that by reading while the command beside it printed a pass, and a
grade disagreeing with its own instrument on the law she has ruled on twice is
the thing worth fixing.

**Two corrections this run made to itself, both caught by somebody else's
check.** The first version of the law 14 verdict set `measure`'s exit code, and
`tests/test_voice_enforcements.py` asserts on that exit code by name. So the
suite reported "a served issue carries a non-ASCII character or an em dash"
about an issue whose em dash count is zero. One return value had been given two
meanings, which is L-A44 in the company standard, and the test was right while
naming the wrong cause. The verdict now lives in `check_voice.py devices` with
an exit code of its own, and `measure` keeps the one meaning a test depends on.

The second is the ledger. This branch merges run 49's escalation row, and

Main is at 206 and the row pushed it to 207, which neither change does alone.
Both missing fields are written in this run rather than the ratchet moved,

## The company standard already names both of this run's findings

`docs/standards/lessons.md` is the owner's corrections generalized across the
portfolio and the charter says to treat a rule in it exactly as a rule from the
charter. It has no `writer` section, so the `any` section is what binds here,
and two of its rules are this run's two findings written a month earlier.

**L-A21, a gate is judged by what it can see, and a gate that saw nothing is a
failure rather than a quiet pass.** Its first clause is "its scope is narrower
than its subject", and it gives a concrete test: name one change that would
break what this gate governs, then ask whether the gate would have seen that
change rather than whether it would have fired on it. `truncations` governs
edit damage in the generator. The change is a trim that takes a bullet's
header. It could not see it, by its first filter. The rule also says every gate
is tested against an artifact known to fail it before the gate is trusted,
which is why both detectors this run touched were run red before green:
`headless` against `origin/main`'s copy of the file, and the law 14 rule
against the live archive.

**L-A47, an instrument's scope is part of its answer, and a scope it does not
state is whatever it happened to be pointed at.** That is the shape count
exactly. It reported "shapes 2" with no statement that one of the two kinds it
counted was a line the generator had no choice about printing, and the grade
beside it quoted the figure.

Neither rule was cited by the gates they describe. That is not a finding
against the standard, which is vendored and read-only here. It is the reason
this seat's gates get run red first from now on, and the reason the ban list's
new entry is written as a question about a diff.
